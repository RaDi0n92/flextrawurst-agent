# Session 2026-05-12 (Session 5)

## Was wurde gemacht

GENI Web (Port 8020) war komplett nicht reagierend via systemd, obwohl manuell startend es funktioniert hat.

**Wurzelursache gefunden und behoben:**  
Drei `async def` Route-Handler machten synchrone Datei-I/O direkt im asyncio Event Loop:

1. `/knoten` (dialog.py:950) — `sorted(glob("*.json"), key=lambda f: f.stat().st_mtime)` auf 800K Dateien, alle 8 Sekunden vom Browser gepolt via `setInterval(knotenLaden, 8000)`
2. `/muster` (dialog.py:996) — `glob("*.json")` über alle 800K Dateien
3. `/api/splitter` (dialog.py:1017) — `glob("*.json")` über alle 800K Dateien für random sampling

In FastAPI: `async def` Routes laufen direkt auf dem Event Loop. Synchrones I/O dort blockiert alles. `def` Routes laufen im Thread Pool — Event Loop bleibt frei.

**Fix:** Alle drei auf `def` geändert + Algorithmus von O(800K-glob) auf O(n-backward-scan) umgeschrieben. IDs sind sequentielle Integers → von max_id rückwärts scannen, kein stat() nötig, kein glob. Response-Zeit: von ∞ auf ~8ms.

**Diagnose-Tool:** `py-spy dump --pid <PID>` hat sofort den blockierenden Stack gezeigt.

## Codewesen-Chat Speedfix (Ende Session)

**Ursache:** dak-gord nutzte num_ctx=8192, codewesen_chat num_ctx=4096 → Ollama lud Modell bei jedem Wechsel neu (~2 Minuten). Dazu: sleep(3) hartkodiert, _kill_fremde-Bug (Bedingung skippte alle Verbindungen), think:False fehlte in reaktion+batch.

**Fixes:**
- codewesen_chat.py: num_ctx 4096→8192, sleep(3) durch Ollama-Idle-Check ersetzt
- codewesen_reaktion.py: think:False + num_ctx=8192 ergänzt
- codewesen_batch_generator.py: think:False + num_ctx 4096→8192
- _stoppe_blocker_und_kill_fremde: Bedingung für Client-Erkennung gefixt
- ollama.service: OLLAMA_NUM_CTX=8192 global gesetzt
