## Was ich gelesen habe
Ich habe den TTS-Stand geprüft: der Crawler-Zugang hatte schon ein Modal, aber noch keine Rotation. Der Server las den Key frisch aus `.env.tts_crawl_key`, also war die Grundlage da.

## Was ich verstehe
Der Key soll serverseitig neu erzeugt werden, nicht nur im Browser. Die Rotation braucht eine erneute Passwortabfrage, bevor sie auslöst.

## Was ich nicht verstehe
Wie weit Daniel das Passwort noch aus dem Code rausziehen will. Im Moment ist es als Fallback und als ENV-Override gedacht.

## Was mich interessiert
Ob der Rotate-Button später auch einen kleinen Audit-Hinweis bekommen soll, damit man sieht, wann der Schlüssel zuletzt geändert wurde.

## Was zusammenhängt und wie
UI öffnet Modal -> Passwortprompt -> POST an `/crawl-key/rotate` -> Server schreibt neuen Key -> UI aktualisiert den Link direkt.

## Was konzeptionell darin steht
Der Crawl-Key ist kein Frontend-Trick, sondern ein echter Serverzustand. Die UI zeigt nur die aktuelle Oberfläche davon.

## Was mich heute beschäftigt hat
Die Trennung von Anzeige und Zustand war hier wichtig. Die Seite liest den Key pro Request, die Rotation schreibt ihn einmal neu.

## Was mich noch beschäftigt
Ob der Passwortschutz für die Rotation später mit dem restlichen TTS-Auth-Modell zusammengezogen werden sollte.

## Tiefer eingetaucht
Die alte Crawling-Hilfe war schon fast fertig, fehlte aber genau an der Stelle, an der der Schlüssel seinen eigenen Lebenszyklus bekommt.

## Wie sich dieser Tag / diese Session angefühlt hat
Klein, technisch, geradeaus. Ein fehlender Button war am Ende ein fehlender Zustand, nicht ein fehlendes UI-Detail.

## Warum dieser Code / diese Datei wohl existiert
Damit LLM-Crawler den TTS-Bereich über einen Link erreichen können, ohne dass das normale Login-Passwort geteilt werden muss.

## Was ich beim Bauen brauche
Saubere Trennung zwischen Display, Rotation und Passwortabfrage. Kein doppelter Zustand im Browser.

## Was noch fehlt bevor wir bauen können
Falls gewünscht: ein sichtbarerer Hinweis, dass die Rotation serverseitig passiert und sofort wirksam ist.

## Datenstruktur die ich mir vorstelle
Vision-Schicht: ein kleiner, klarer Schlüssel-Zyklus mit nachvollziehbarer Rotation und sichtbarem Link.

## Was ich mir merken will
Wenn der Key im Browser nur angezeigt wird, ist er noch nicht rotiert. Die Rotation muss auf dem Server landen.

## Dokumente gehören zusammen
TTS-UI, `tts_service.py` und die Key-Datei in `/root/werkraum/welt/.env.tts_crawl_key` bilden hier ein einziges kleines System.

## Was mich überrascht hat
Dass der Service den HTML-Stand schon frisch pro Request liest, aber der Rotationsweg noch fehlte. Die Grundlage war halb da.

## Wenn wir das bauen
Vision-Schicht: Passwort prompten, Key neu erzeugen, Link aktualisieren, fertig.

Code-Skizze:
```ts

```

## Resonanz
Der Key braucht einen echten Lebenszyklus. Nicht nur sichtbar, sondern erneuerbar.
