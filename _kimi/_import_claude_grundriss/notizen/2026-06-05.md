## Was zusammenhängt und wie

- Events-Tabelle → `visibility_layer` ist der einzige Hebel. String-Feld, kein Schema-Change nötig.
- `/weltstrom` Endpoint → baut auf `/events` auf, fügt Abstraktion hinzu (`_weltstrom_beschreibung`).
- `serve_process_camera_preview.ts` → leitet `/api/*` weiter, deshalb musste die Fetch-URL `/api/weltstrom` sein — nicht `/weltstrom`.
- `cinema_script.html` → lebt jetzt als eigenständige Datei, `generateHTML()` liest sie per `readFileSync`. Nie wieder durch Build verlierbar.

## Was konzeptionell darin steht

Die Drei-Tier-Sichtbarkeit (PUBLIC/WORLD/INTERNAL) ist eine elegante Lösung: nicht alles zeigen, nicht alles verstecken. WORLD-Events werden abstrahiert — kein actor_id, keine internen IDs, nur menschlicher Text. Das respektiert die Integrität der Welt ohne sie zu verschließen.

## Tiefer eingetaucht

## Datenstruktur die ich mir vorstelle

**Vision-Schicht:** Ein Admin-Tool das alte Events migriert — "zeige mir alle Events der letzten 30 Tage die `internal` sind aber eigentlich `world` sein sollten, und setze sie um."

**Code-Skizze:**
```python
# einmalige Migration
cur.execute("""
  UPDATE events SET visibility_layer='world'
  WHERE event_type IN ('wesen.nachricht_erhalten','wesen.vernachlaessigt','weltklima.tick')
  AND visibility_layer='internal'
  AND created_at > NOW() - INTERVAL '30 days'
""")
```
