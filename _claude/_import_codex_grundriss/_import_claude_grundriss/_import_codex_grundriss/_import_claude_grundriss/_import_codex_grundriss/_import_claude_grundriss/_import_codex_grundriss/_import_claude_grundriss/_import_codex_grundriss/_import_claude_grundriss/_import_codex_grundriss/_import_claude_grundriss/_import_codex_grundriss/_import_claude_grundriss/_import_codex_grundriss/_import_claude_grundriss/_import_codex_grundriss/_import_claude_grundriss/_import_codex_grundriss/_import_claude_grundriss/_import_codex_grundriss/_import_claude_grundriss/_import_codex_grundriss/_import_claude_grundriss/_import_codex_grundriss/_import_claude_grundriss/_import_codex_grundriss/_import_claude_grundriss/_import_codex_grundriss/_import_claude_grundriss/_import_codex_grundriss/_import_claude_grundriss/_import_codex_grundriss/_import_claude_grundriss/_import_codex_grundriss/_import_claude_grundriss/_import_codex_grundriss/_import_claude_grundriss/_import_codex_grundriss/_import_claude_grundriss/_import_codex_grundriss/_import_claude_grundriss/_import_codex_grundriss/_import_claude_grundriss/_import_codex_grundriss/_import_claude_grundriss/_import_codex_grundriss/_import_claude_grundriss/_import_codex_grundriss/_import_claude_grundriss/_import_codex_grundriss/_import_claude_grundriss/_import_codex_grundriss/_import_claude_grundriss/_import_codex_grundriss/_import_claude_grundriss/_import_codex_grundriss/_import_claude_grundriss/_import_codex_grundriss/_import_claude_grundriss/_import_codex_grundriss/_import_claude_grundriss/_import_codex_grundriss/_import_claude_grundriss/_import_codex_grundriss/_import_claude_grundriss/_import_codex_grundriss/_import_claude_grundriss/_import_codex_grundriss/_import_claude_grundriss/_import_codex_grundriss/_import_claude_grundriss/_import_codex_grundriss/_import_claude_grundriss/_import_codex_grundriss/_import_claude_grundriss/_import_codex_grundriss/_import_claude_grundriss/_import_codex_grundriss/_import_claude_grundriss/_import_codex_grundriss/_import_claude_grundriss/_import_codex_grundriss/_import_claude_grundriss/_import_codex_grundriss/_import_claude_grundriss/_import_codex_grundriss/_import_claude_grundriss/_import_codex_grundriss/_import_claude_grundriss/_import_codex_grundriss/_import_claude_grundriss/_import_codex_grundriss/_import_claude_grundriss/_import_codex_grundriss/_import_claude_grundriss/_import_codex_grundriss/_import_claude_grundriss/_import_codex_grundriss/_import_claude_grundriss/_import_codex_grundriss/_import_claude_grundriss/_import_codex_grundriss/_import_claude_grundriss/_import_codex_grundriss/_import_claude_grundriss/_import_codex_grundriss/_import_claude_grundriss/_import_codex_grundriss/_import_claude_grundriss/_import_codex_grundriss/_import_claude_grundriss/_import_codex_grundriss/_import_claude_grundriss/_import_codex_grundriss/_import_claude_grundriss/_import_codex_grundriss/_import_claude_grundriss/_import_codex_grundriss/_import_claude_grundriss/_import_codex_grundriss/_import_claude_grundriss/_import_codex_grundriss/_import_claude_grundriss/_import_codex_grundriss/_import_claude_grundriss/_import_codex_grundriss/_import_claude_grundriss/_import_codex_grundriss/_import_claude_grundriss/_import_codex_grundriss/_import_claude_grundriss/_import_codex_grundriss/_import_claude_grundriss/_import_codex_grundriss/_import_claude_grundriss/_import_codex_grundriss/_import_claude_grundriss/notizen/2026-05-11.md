## Session 7 — KompOase-Datenfeed vollständig verbunden

### Kontext

Nach Session 6 war der Datenfeed zwar eingebaut (`splitterUpdate`-Script am Ende von
`kompoase.html`), aber `fetchSplitter()` ignorierte ihn noch komplett: Im Theater-Modus
liefen synthetische Splitter, im Non-Theater-Modus rief die Funktion nur `/api/splitter`
(alter GENI-Endpunkt, Port 8020) auf. Die DB-Splitter kamen nirgends an.

### Was gemacht

**Proxy-Analyse**: `/api/zwischenraum/splitter` lief bereits durch den bestehenden
`/api/*`-Handler in `serve_process_camera_preview.ts` — kein Code-Änderung nötig.
Der Handler schließt nur `/api/splitter` aus (GENI-Proxy), alles andere geht durch zu
Port 8030. Test bestätigt: count=21, aktiv=20, geisterreste=1.

**`fetchSplitter()` chirurgisch umgebaut** (nur diese eine Funktion, nichts sonst):
- Wenn `THEATER=true`: unverändert → `theaterSplitter(50)` 
- Wenn `THEATER=false`: beide Quellen parallel mit eigenem try/catch
  - GENI: `/api/splitter?n=60` → läuft weiter wenn erreichbar
  - DB: `/api/zwischenraum/splitter?limit=200` → neu
  - DB-Format → Konstruktor-Mapping:
    - `essenz` → `inhalt_kurz` + `inhalt_voll`
    - `pos_x/pos_y` → `position.x/y`
    - `vel_x/vel_y` → `velocity.x/y`
    - `entity_id` → `quelle_id` (HF-Farbtabelle greift: namelessAI_1234 → #4488ff)
    - `energie` + `status='geisterrest'` → energie=0.08
    - `groesse` aus energie abgeleitet (0.4 + energie*1.2)
    - `synthetisch: false` (echte Daten)
  - Console-Log: `[DATEN] GENI: N Splitter, DB: M Splitter`
  - Fehler in einer Quelle stoppt die andere nicht

**Node-Server**: läuft als `process-camera-preview.service` (nicht manuell, war nicht
klar) → `systemctl restart process-camera-preview.service`

### Getestet

```
curl -u "werkraum:..." http://localhost:8787/api/zwischenraum/splitter?limit=5
→ count=5, aktiv=5, entity_id=namelessAI_1234, essenz="Ich beobachte wie..."
```

Proxy leitet korrekt weiter. Mapping stimmt. Browser-Konsole wird bei THEATER=false
zeigen: `[DATEN] GENI: 0 Splitter, DB: 21 Splitter` (GENI läuft, 0 wenn offline).

### Was jetzt möglich ist

Wenn jemand den Theater-Button ausschaltet, landen echte DB-Splitter in der Physik-
Simulation — mit echten Koordinaten, Geschwindigkeiten, Energien aus der Datenbank.
Die Herkunftsfarben greifen automatisch (entity_id passt zu HF-Tabelle). Geisterreste
werden mit gedämpfter Energie (0.08) ins System eingespeist und pulsieren entsprechend.

### Offen

- `fetchSplitter()` im Non-Theater-Modus pollt noch alle 30s via `POLL`-Konstante in
  `laden()` — das ist der interne Timer, unabhängig vom `splitterUpdate`-Event. Der
  externe Datenfeed (zweites Script-Tag) und der interne Fetch sind noch zwei Systeme.
  Zusammenführen wäre der nächste saubere Schritt.
- Splitter aus DB haben noch keinen `thema_vektor` — wird random erzeugt. Wenn
  `thematische_tags` aus der DB genutzt würden (z.B. Hash der Tags → Vektor), würde
  die Physik semantisch kohärenter: gleichthematische Splitter zögen sich an.
- HF-Farbtabelle im HTML hat noch die alten namelessAI_NNNN_NNNN-IDs — die echten
  entity_ids aus der DB sind `namelessAI_1234` etc. Farbe greift trotzdem für _1234,
  nicht für die anderen 5 Wesen. Tabellenabgleich steht aus.
